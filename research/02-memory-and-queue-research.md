# Background Removal Service — исследование ограничений памяти и архитектуры очереди

## 1. Цель документа

Этот документ фиксирует проблему, обнаруженную во время разработки и тестирования MVP сервиса удаления фона, а также описывает принятое архитектурное решение.

Первоначально предполагалось, что несколько ML-моделей будут постоянно загружены в оперативную память и доступны для быстрого переключения на фронтенде. Такой подход должен был уменьшить задержку перед инференсом, поскольку модель не требовалось бы загружать перед каждым запросом.

Во время тестирования на целевом VPS выяснилось, что доступных ресурсов недостаточно для безопасного одновременного хранения нескольких ONNX-моделей и параллельной обработки запросов.

## 2. Конфигурация инфраструктуры

Тестирование выполнялось на VPS со следующими характеристиками:

- 8 vCPU;
- 12 ГБ оперативной памяти;
- 100 ГБ NVMe;
- Ubuntu 24.04 LTS;
- Docker и Docker Compose;
- Python;
- `rembg`;
- ONNX Runtime;
- CPU inference без GPU.

На сервере одновременно размещаются:

- Nginx;
- Nuxt 4 / Nitro;
- Python gRPC backend;
- ML-модели;
- системные процессы операционной системы.

Следовательно, Python-сервис не может использовать все 12 ГБ RAM: часть памяти необходима операционной системе, Docker, Nginx и frontend-контейнеру.

## 3. Первоначальная архитектура

На первом этапе использовалась следующая схема:

```text
Запуск backend
  |
  v
Загрузка всех включённых моделей
  |
  v
Хранение ONNX Session в памяти
  |
  v
Получение запроса
  |
  v
Использование уже загруженной модели
```

Для каждой модели создавалась отдельная ONNX Session, которая сохранялась в словаре и повторно использовалась при следующих запросах.

Преимуществом такого подхода было небольшое время ожидания перед инференсом: модель уже находилась в памяти.

Однако такая архитектура плохо подходит для VPS с ограниченным объёмом RAM.

## 4. Обнаруженная проблема

Во время запуска и последовательного использования моделей было установлено, что тяжёлая модель может занимать несколько гигабайт оперативной памяти.

При загрузке нескольких моделей происходило следующее:

1. backend загружал первую модель;
2. ONNX Runtime выделял память под веса и внутренние структуры;
3. загружалась следующая модель;
4. общее потребление памяти приближалось к доступному объёму VPS;
5. при запуске инференса требовалась дополнительная память для входных данных, промежуточных тензоров и результата;
6. Linux завершал процесс backend из-за нехватки памяти.

На практике VPS с 12 ГБ RAM оказалось недостаточно для безопасного одновременного хранения всех выбранных моделей.

Особенно опасной была ситуация, когда тяжёлая модель уже занимала значительную часть памяти, а пользователь запускал обработку другой моделью. Даже если вторая модель была легче, суммарное потребление памяти приводило к аварийному завершению Python-процесса.

## 5. Почему простого ограничения параллельности оказалось недостаточно

Первым возможным решением было ограничить одновременный инференс с помощью `asyncio.Semaphore(1)`.

Такая схема разрешает выполнять только одну обработку одновременно:

```text
Запрос 1 -> обработка
Запрос 2 -> ожидание
Запрос 3 -> ожидание
```

Однако semaphore ограничивает только количество одновременно выполняющихся операций. Он не освобождает память, занятую уже загруженными моделями.

Если все модели продолжают храниться в памяти, общий расход RAM остаётся высоким независимо от того, сколько запросов выполняется одновременно.

Поэтому ограничение параллельности само по себе не решило проблему.

## 6. Эксперимент с очисткой памяти

После завершения обработки были добавлены:

- удаление ссылок на ONNX Session;
- вызов `gc.collect()`;
- вызов `malloc_trim(0)` в Linux;
- удаление локальных ссылок на входное изображение.

Пример логики:

```python
session = None
gc.collect()
malloc_trim(0)
```

Это позволило вернуть часть освобождённой памяти операционной системе.

Однако необходимо учитывать особенности Python, ONNX Runtime и системного аллокатора:

- удаление Python-объекта не гарантирует немедленный возврат всей памяти ОС;
- ONNX Runtime может использовать собственные memory pools;
- системный аллокатор может оставлять освобождённые блоки внутри процесса для повторного использования;
- пиковое потребление памяти во время инференса может быть выше размера самой модели.

Поэтому очистка памяти уменьшила риск, но не позволила безопасно хранить несколько тяжёлых моделей одновременно.

## 7. Принятое решение: загрузка модели на один запрос

Для MVP было принято решение не хранить модели в оперативной памяти между запросами.

Новая схема обработки:

```text
Получение задачи
  |
  v
Загрузка выбранной модели
  |
  v
Создание ONNX Session
  |
  v
Инференс
  |
  v
Формирование PNG
  |
  v
Удаление ONNX Session
  |
  v
Сборка мусора и освобождение памяти
```

Модель загружается непосредственно перед обработкой конкретного изображения и выгружается после завершения.

### Преимущества

- в памяти находится только одна модель;
- потребление RAM становится предсказуемым;
- можно использовать модели разного размера;
- снижается вероятность аварийного завершения backend;
- сервис может работать на существующем VPS с 12 ГБ RAM.

### Недостатки

- перед каждым инференсом требуется повторная загрузка модели;
- увеличивается общее время обработки;
- пропускная способность сервиса ограничивается одним worker.

Для MVP надёжность была признана важнее минимальной задержки.

## 8. Проблема одновременных запросов

После перехода на загрузку модели для каждого запроса появилась новая потенциальная проблема.

Если несколько запросов начнут выполняться одновременно, каждый из них создаст собственную ONNX Session:

```text
Запрос 1 -> загрузка модели A
Запрос 2 -> загрузка модели B
Запрос 3 -> загрузка модели C
```

В этом случае потребление памяти снова может превысить доступные 12 ГБ.

Следовательно, необходимо было гарантировать, что в любой момент времени выполняется только одна ML-задача.

## 9. Очередь задач и один worker

Для контроля нагрузки была реализована очередь задач.

Архитектура:

```text
Пользовательские запросы
  |
  v
Очередь максимум из 10 ожидающих задач
  |
  v
Один worker
  |
  v
Загрузка выбранной модели
  |
  v
Инференс
  |
  v
Выгрузка модели
  |
  v
Следующая задача
```

Основные свойства решения:

- одновременно обрабатывается только одно изображение;
- в памяти одновременно находится только одна ML-модель;
- до 10 изображений могут ожидать обработки;
- одиннадцатая ожидающая задача отклоняется;
- frontend показывает пользователю актуальную позицию в очереди.

Если очередь заполнена, клиент получает сообщение:

> На сервисе сейчас высокая нагрузка. Попробуйте отправить изображение позже.

## 10. Изменение gRPC-контракта

Первоначально обработка выполнялась одним долгим RPC:

```proto
rpc RemoveBackground(RemoveBackgroundRequest)
    returns (RemoveBackgroundResponse);
```

После добавления очереди такой контракт стал неудобным. HTTP-запрос мог оставаться открытым длительное время, а frontend не мог показать пользователю позицию в очереди.

Поэтому взаимодействие было разделено на три RPC-метода:

```proto
rpc SubmitJob(SubmitJobRequest)
    returns (SubmitJobResponse);

rpc GetJobStatus(GetJobStatusRequest)
    returns (GetJobStatusResponse);

rpc GetJobResult(GetJobResultRequest)
    returns (GetJobResultResponse);
```

### Последовательность работы

```text
1. Frontend отправляет изображение через SubmitJob.
2. Backend возвращает job_id и позицию в очереди.
3. Frontend периодически вызывает GetJobStatus.
4. Backend возвращает queued, processing, completed или failed.
5. После completed frontend вызывает GetJobResult.
6. Backend возвращает PNG и удаляет результат из памяти.
```

Для обновления позиции используется polling с интервалом около 1,5 секунды.

Для MVP polling выбран вместо WebSocket или SSE, поскольку он проще в реализации и достаточен для очереди небольшого размера.

## 11. Статусы задачи

Используются следующие статусы:

- `queued` — задача находится в очереди;
- `processing` — worker загружает модель или выполняет инференс;
- `completed` — результат готов;
- `failed` — обработка завершилась ошибкой.

Frontend отображает состояние пользователю:

```text
Добавляем изображение в очередь...
Ваша позиция в очереди: 4
Удаляем фон...
Результат готов
```

## 12. Ограничение размера очереди

Размер очереди ограничен десятью ожидающими задачами.

Это решение принято по нескольким причинам:

- входные изображения хранятся в RAM до начала обработки;
- максимальный размер одного файла составляет 10 МБ;
- десять файлов могут занять около 100 МБ без учёта накладных расходов;
- большая очередь значительно увеличила бы время ожидания;
- сервис не должен принимать больше задач, чем способен обработать за разумное время.

Текущая схема допускает:

- одну активную задачу;
- до десяти ожидающих задач.

## 13. Итоговая архитектура

```text
Browser
  |
  | HTTP
  v
Nginx
  |
  v
Nuxt 4 / Nitro BFF
  |
  | gRPC
  v
Python backend
  |
  +-- ModelRegistry
  |
  +-- JobQueue
  |     |
  |     +-- максимум 10 ожидающих задач
  |
  +-- один worker
        |
        +-- загрузка модели
        +-- инференс
        +-- выгрузка модели
        +-- очистка памяти
```

## 14. Результат

После изменения архитектуры удалось добиться следующих результатов:

- backend стабильно работает на VPS с 12 ГБ RAM;
- несколько ONNX-моделей не хранятся одновременно в памяти;
- исключена параллельная загрузка тяжёлых моделей;
- сервис не завершается при нескольких одновременных запросах;
- пользователи могут отправлять изображения в очередь;
- frontend показывает актуальную позицию;
- при высокой нагрузке новые запросы корректно отклоняются;
- инфраструктуру не потребовалось переносить на более дорогой VPS.

## 15. Компромиссы решения

Принятое решение является компромиссом между скоростью и стабильностью.

### Потери

- увеличилось время обработки из-за повторной загрузки модели;
- одновременно выполняется только одна задача;
- очередь и результаты хранятся в памяти одного процесса;
- после перезапуска backend незавершённые задачи теряются.

### Выигрыш

- предсказуемое потребление памяти;
- устойчивость к одновременным запросам;
- возможность использовать тяжёлые модели на ограниченной инфраструктуре;
- простая архитектура без Redis и внешнего task broker;
- достаточная надёжность для MVP.

## 16. Возможные улучшения после MVP

Для production-версии можно рассмотреть:

- перенос очереди в Redis;
- Celery, Dramatiq или другой task broker;
- хранение результатов в S3-совместимом object storage;
- TTL для завершённых и упавших задач;
- автоматическое удаление невостребованных результатов;
- отдельные worker-пулы для лёгких и тяжёлых моделей;
- запуск GPU inference;
- масштабирование worker-контейнеров;
- маршрутизацию задач по доступной памяти;
- кэширование последней использованной модели;
- метрики Prometheus и мониторинг Grafana.

Эти улучшения не требуются для текущего MVP, но позволяют масштабировать сервис при росте нагрузки.

## 17. Вывод

VPS с 12 ГБ RAM оказался недостаточным для первоначальной архитектуры, в которой несколько ONNX-моделей постоянно хранились в памяти.

Простого ограничения параллельности было недостаточно, поскольку память продолжали занимать сами модели. Поэтому архитектура была изменена: модель загружается только для обработки конкретной задачи и выгружается после завершения.

Чтобы исключить одновременную загрузку нескольких моделей, был реализован один worker и ограниченная очередь на десять ожидающих изображений.

Такое решение увеличивает время обработки, но обеспечивает стабильную работу сервиса на доступной инфраструктуре. Для MVP этот компромисс является оправданным: надёжность и предсказуемое использование памяти важнее максимальной пропускной способности.
